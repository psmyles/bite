# Moving the editor from wgpu to sokol_gfx + sokol_imgui

## Why

Measured on 2026-09-21 (RTX 4080, driver 32.0.15.9159, Ryzen 9 7900, Windows 11), the editor's
startup is two-thirds graphics-stack bring-up and its memory footprint is almost entirely wgpu:

| | bite-gui today (wgpu / DX12) | fire (sokol_gfx / D3D11) |
|---|---|---|
| Process start → first frame presented | ~590 ms | ~147 ms |
| Of which GPU bring-up | ~385 ms | ~127 ms (on a thread, mostly hidden) |
| RAM the GPU stack adds | +137 MB working set / +315 MB commit | +23 MB / +50 MB |
| Steady after settle | 172 MB working set / 325 MB commit | 53 MB / 64 MB |

The editor's own work - logging, cache prune, event loop, `Editor::new`, the window, the font
atlas, the first draw - is about 195 ms and a 19 MB working set. Everything else is wgpu.

An isolated bring-up benchmark (same process shape, device held alive) shows the cost is wgpu's
abstraction, not the API generation underneath it:

| Backend | Time to device | Working set | Commit |
|---|---|---|---|
| Raw D3D11 (what sokol_gfx sits on) | 127 ms | 32 MB | 49 MB |
| Raw D3D12 | 141 ms | 44 MB | 55 MB |
| wgpu on DX12 | 273 ms | 144 MB | 316 MB |

wgpu's `request_adapter` alone is ~233 ms and +52 MB (it enumerates and probes every DXGI adapter;
this machine has three), and `request_device` + pipeline creation is ~95 ms and +82 MB (naga
compiling WGSL to HLSL at runtime, `gpu-allocator` heaps, the D3D12 runtime).

**Targets.** Warm start → first frame **≤ 300 ms** (expected ~250 ms with the bring-up on a
thread), steady working set **≤ 70 MB**, and `--capture` output matching the goldens taken
before the migration.

## What the result looks like

Fire's shell, transplanted, including its ImGui layer. winit keeps the window, the event loop
and input; sokol_gfx replaces wgpu as the one drawing API, on a D3D11 device and DXGI flip-model
swapchain the shell creates; Dear ImGui moves from 1.90.9 to **1.92.9b** - the version fire's
`sokol_imgui.h` is compiled against - and `sokol_imgui` renders it, fonts included, through the
1.92 texture protocol. `bite-imgui` keeps its safe API (widgets, draw lists, styles, `Face`), so
the 13k lines of editor code above it change only where they touch textures. The owned renderer
(`renderer.rs`, `shader.wgsl`) is deleted, not ported: sokol_imgui is that renderer, maintained
next to sokol_gfx by its author, and the same header on every OS.

```
crates/bite-imgui-sys/
├── vendor/cimgui/       cimgui bf9b984 + Dear ImGui 1.92.9b docking - the tree dear-imgui-sys
│                        0.17.0 ships, byte-identical to what fire's simgui compiles against
├── src/bindings.rs      regenerated by `cargo run --example generate_bindings --features bindgen`
└── build.rs             compiles imgui + cimgui; the define list `bite-gui/build.rs` must mirror
crates/bite-imgui/src/
├── font.rs              dynamic fonts: one ImFont per (family, weight), size chosen at PushFont
└── lib.rs               Frame::submit() - no igRender, no draw-data copy; sokol_imgui does both
crates/bite-gui/
├── simgui/              simgui.c + sokol_imgui.h (fire's), compiled by build.rs against the same
│                        cimgui.h bite-imgui-sys builds
├── src/platform.rs      window + event loop; owns the swapchain and the frame
├── src/render/
│   ├── d3d11.rs         Device (create, fill_environment) + Swapchain (new, resize, acquire, present)
│   ├── metal.rs         the macOS twin: CAMetalLayer, MTLDevice, nextDrawable
│   ├── imgui.rs         simgui_setup once, simgui_render per frame, simgui_imtextureid
│   ├── textures.rs      the UI's image store: key → (sg::Image, sg::View, ImTextureID)
│   └── readback.rs      render target → Vec<u8> through sg::d3d11_query_image_info (for smoke)
├── src/timing.rs        BITE_TIMING startup breakdown, process-creation clock, first-frame stamp
└── src/smoke.rs         offscreen capture on an sg attachments pass + readback.rs
scripts/ttfp.ps1         loops launches, reports first-frame time and memory (copy of fire's)
vendor/sokol-rust/       pinned copy of floooh/sokol-rust @ b22a545, the revision fire vendors
```

No shader source, no shader compiler, no `gen-shaders.sh`: sokol_imgui carries its own shaders
as embedded bytecode for every backend.

## Decisions

**D1 - sokol_gfx over D3D11 on Windows; Metal later.** The measured win is on Windows, which is
what ships. The Metal twin is fire's `render/metal.rs`, copied when macOS is next on the list.

**D2 - Upgrade Dear ImGui to 1.92.9b and render with sokol_imgui.** `bite-imgui` today is on
1.90.9 with the classic `GetTexDataAsAlpha8` atlas and copies every frame's draw lists into owned
Rust vectors for the owned renderer. sokol_imgui needs the 1.92 texture protocol and calls
`igRender` itself. Upgrading buys three things beyond the renderer: no atlas build at startup
(1.92 rasterizes glyphs on first use; fire measures font registration at ~0.4 ms), no atlas
rebuild on a DPI change (`style.FontScaleDpi`), and one ImGui version across bite, fire and
3d-review. The `Face` model - family, weight, logical size - survives unchanged as the public API;
underneath it becomes one `ImFont` per family and weight, with the size passed to
`igPushFont(font, size)`.

**D3 - Keep `bite-imgui-sys`; replace its vendored tree and regenerate.** The alternative,
building `bite-imgui` on `dear-imgui-sys` as fire does, would rename every symbol the wrapper
uses (`ImVec2` → `ImVec2_c` and so on) across five files for no gain. `bite-imgui-sys` already
has the bindgen example; pointing it at the 1.92.9b `cimgui.h` gives the same `ig*`/`Im*` names
back. The tree is taken from `dear-imgui-sys 0.17.0`'s `third-party/` (cimgui bf9b984, docking
branch, freetype API declared but not compiled) so bite's `cimgui.h` is the file fire's
`simgui/cimgui.h` is a copy of. `vendor/imgui-node-editor` is not compiled or referenced by
anything and goes.

**D4 - The shell owns the device and the swapchain.** sokol_gfx is handed a device at `sg::setup`
and a render-target view per frame; it never touches a window. `render/d3d11.rs` is fire's file
with the names changed - same `D3D11CreateDevice` with WARP fallback (RDP, headless CI), same
`FLIP_DISCARD` two-buffer chain, same `Present(1, 0)` and `DXGI_STATUS_OCCLUDED` handling.

**D5 - Layout stays in logical pixels.** bite lays out in logical pixels with
`io.DisplayFramebufferScale = scale`; fire lays out in physical pixels with the platform backend
locked to 1.0. sokol_imgui supports both - it sizes the viewport from
`DisplaySize × DisplayFramebufferScale` and scales clip rects the same way - so bite keeps its
coordinate space and the panels, splitters and canvas code do not change.

**D6 - Offscreen capture stays in-process and reads back through the native handle.** sokol_gfx
has no `read_pixels`; 3d-review's `read_image_subresource`
(`crates/render/src/rhi/backend/d3d11.rs:690-780`) does it with `sg::d3d11_query_image_info`, a
staging texture and `Map`. Copy it into `render/readback.rs`. `simgui_render` draws into
whatever pass is open, so an attachments pass captures exactly what the window would show.

**D7 - The `windows` crate, D3D11 + DXGI features only.** It is already in `Cargo.lock` (0.62.2,
pulled by wgpu today), so the dependency swap adds nothing new to the tree; wgpu, pollster and
their ~40 transitive crates leave. Pin the feature list to what `d3d11.rs` and `readback.rs` name,
as fire's `Cargo.toml` does.

**D8 - Startup timing becomes a permanent, file-sinked instrument.** The experiment used
temporary probes and stderr through a redirected pipe, and the four pre-window steps all read as
~22 ms, which is suspicious enough to re-baseline properly. Fire's pattern: `FIRE_TIMING=<path>`
appends lines; the origin is the kernel's process-creation time (`GetProcessTimes`), so the loader
and CRT are counted; a first-frame stamp; a harness script that loops launches.

## The launch-time optimisations fire does, and where each lands here

The measured warm timeline of bite-gui today, and what each item does to it:

```
   0 ms  main
  23 ms  run()                       attach_parent_console
  45 ms  prune_cache done            L3: off the critical path
  69 ms  event loop built
  92 ms  resumed → create()
 117 ms  Editor::new                 (node definitions; Session::load - L3: loaded twice today)
 155 ms  window created              (icon PNG decoded first - L4)
 194 ms  wgpu Instance               ─┐
 215 ms  create_surface               │
 429 ms  request_adapter              │ L1: replaced by a D3D11 device made on a thread since main;
 513 ms  device + pipelines           │     L2: sokol_imgui's pipeline from embedded bytecode, ~1 ms
 519 ms  surface configured          ─┘
 522 ms  imgui Context (fonts)       ─┐ L7: 1.92 registers fonts without rasterizing; the atlas
 548 ms  font atlas uploaded         ─┘     upload happens inside the first simgui_render
 563 ms  FIRST FRAME
```

**L1 - GPU bring-up on its own thread, started at the top of `main`.** Fire's
`render::gpu::Gpu::start` spawns `bring_up` (device → `sg::setup` → pipelines) before the event
loop exists and the first window joins the handle. In bite that thread runs alongside
`attach_parent_console`, logging, the event loop, `Editor::new` and window creation - ~155 ms of
serial work that today happens *before* the GPU is even touched. D3D11 devices are free-threaded;
sokol_gfx has no thread affinity, only a single-user rule, and the join is the hand-off. The only
per-window piece, the swapchain, is 2 ms on the main thread after the join. `simgui_setup` can
also run on that thread (it needs sokol_gfx, not a window), as long as the ImGui context it is
paired with is created on the main thread after the join - see Phase 3.

**L2 - No shader compilation at launch.** Today naga translates WGSL and D3D compiles HLSL inside
the 95 ms "device + pipelines" step. sokol_imgui's shaders are embedded DXBC/MSL/SPIR-V; fire's
whole pipeline step is 0.8 ms.

**L3 - File-system chores off the critical path.** Done in Phase 5 except the log header, which
was left alone: `logging::start_session` is one `OpenOptions` and one `writeln!`, it is the first
thing that must work if anything later goes wrong, and making it lazy would trade that for no
measurable time. The other two are done.
- `work::prune_cache` walks the thumbnail cache and deletes stale files; nothing waits on it.
  Spawn it; it already tolerates a missing directory.
- `persist::Session::load` runs in `Editor::new` *and* again in `App::create`. Load once and
  hand it over.

**L4 - Decode the window icon at build time.** `icon::window_icon` decodes `icon-256.png` with
the `png` crate on the critical path, before the window exists. Fire's `build.rs::decode_logo`
writes raw RGBA to `OUT_DIR` and the app `include_bytes!` it. Small, but it is on the serial path
and it is free. (`png` stays a dependency for `--capture`'s writer.)

**L5 - The update check** already runs on a thread. Nothing to do.

**L6 - Open the initial workflow while the GPU comes up.** Fire submits the decode of the file it
was launched with before the window exists. The analogue - parsing a `.bite` given on the command
line on a thread and applying it in `create()` - is cheap and worth doing once L1 is in, but it is
not on the first-frame path today (`commands::open_path` runs after the first frame's state is
built), so it is listed last.

**L7 - No font atlas at startup.** Comes free with D2. Today `Fonts::build` rasterizes six faces
at every stylesheet size and uploads the atlas before the first frame (~30 ms). In 1.92 the six
`AddFontFromMemoryTTF` calls bake nothing; glyphs are rasterized as they are first drawn and
uploaded by sokol_imgui through `ImTextureData` inside the frame that needs them. The first frame
pays for the glyphs it shows and nothing else; a DPI change is `style.FontScaleDpi = scale` with
no rebuild.

## Phases

Each phase ends with something that builds, runs and is measured. The two big axes - the ImGui
version and the graphics stack - are changed in separate phases, each checked against the
goldens, so a regression has one cause. The wgpu path stays alive until Phase 7.

### Phase 0 - Instruments and goldens (before touching anything)

1. Add `timing.rs`: `BITE_TIMING=<path>` sink, `ms_since_process_creation()` on the
   `GetProcessTimes` clock (fire's `ttfp.rs`, Windows arm), `report(&str)` stamping working set
   and commit via `K32GetProcessMemoryInfo`, and a first-present stamp with
   `BITE_EXIT_AFTER_FIRST_FRAME` that sleeps 1.5 s, reports, and exits.
2. Mark the phases in `main`, `platform::run` and `App::create` as listed above.
3. Add `scripts/ttfp.ps1` (fire's, renamed): N launches, medians of first-frame time, working set
   and commit.
4. Record the wgpu baseline in this document's *Results* section.
5. Capture the goldens: `bite-gui --capture test_images/goldens/wgpu` for every scene at scale 1
   and 2. Phases 1 and 4 are checked against these.

*Done when:* the baseline table is filled in from the file sink and the goldens are captured.

**Landed.** `crates/bite-gui/src/timing.rs` is the sink; `scripts/ttfp.ps1` the harness (N warm
launches plus a discarded warm-up, medians of first frame / working set / commit, `-Breakdown`
for the phase list); `crates/bite-gui/examples/capture_diff.rs` the check Phases 1 and 4 are
measured with - per-scene differing-pixel count and largest per-channel delta, so "1 LSB of blend
rounding" and "the glyphs moved" cannot be mistaken for each other. Two back-to-back capture runs
of the same binary come out byte-identical, so any later difference is a real one.

The goldens live in `test_images/goldens/wgpu` (50 PNGs, 8.6 MB: 25 scenes x scale 1 and 2).
`test_images/` is gitignored and they stay there rather than being committed - they are a
reference for the span of this migration, re-creatable from the tagged commit in one command, and
not worth 8.6 MB of history.

**The ~22 ms steps were the pipe.** With the file sink the four pre-window phases land 0.6-5 ms
apart, not 22. Nothing in `main`, `run()` or `prune_cache` was ever slow; the experiment was
measuring its own redirected stderr. This also moves the honest baseline from 590 ms to **424 ms**
- the 590 included ~166 ms of measurement overhead - and it changes what L3 is worth (see below).

### Phase 1 - Dear ImGui 1.92.9b, still on wgpu

The upgrade on its own, using 1.92's *legacy* atlas path so the owned wgpu renderer keeps working
unchanged and any pixel difference is ImGui's, not the renderer's.

1. `bite-imgui-sys/vendor/cimgui` ← `~/.cargo/registry/src/*/dear-imgui-sys-0.17.0/third-party/`
   (`cimgui.h`, `cimgui.cpp`, `cimconfig.h`, `imgui/`). Delete `vendor/imgui-node-editor`.
   `build.rs` adds `imgui_freetype.cpp`? No - the header declares the freetype API but nothing
   calls it; leave the source list as it is.
2. `cargo run -p bite-imgui-sys --example generate_bindings --features bindgen`. Commit the new
   `bindings.rs`.
3. `cargo build -p bite-imgui` and fix what the compiler lists. Known from reading the wrapper:
   - `io.FontGlobalScale` is gone. Its job - glyph metrics in logical units while rasterizing at
     physical size - is `style.FontScaleDpi = 1.0` with the atlas rasterized at logical size
     × `DisplayFramebufferScale`; in this phase, since the legacy path builds the atlas once at
     the registered sizes, keep registering each `Face` at its physical size and set
     `ImFontConfig::RasterizerDensity = scale` instead of dividing by it afterwards. Verify with
     `bite-imgui`'s existing mono-advance test.
   - `ImFont::Scale` is gone. The exact-vs-rounded-height correction it carried is unnecessary
     in 1.92, where sizes are floats; delete it and re-run the same test.
   - `igPushFont(font)` → `igPushFont(font, size)`. `with_font` passes the face's logical size.
   - `ImDrawCmd::TextureId` → `ImDrawCmd_GetTexID(cmd)` in `Frame::render`'s copy loop.
   - Anything else the compiler names.
   `IMGUI_DISABLE_OBSOLETE_FUNCTIONS` stays *off* in this phase; `GetTexDataAsAlpha8` and
   `SetTexID` are the legacy path this phase depends on.
4. Run the editor. Diff `--capture` against the Phase 0 goldens.

*Done when:* the editor runs on 1.92.9b with wgpu, the `bite-imgui` tests pass, and the capture
diff is explained (font rasterization moved from stb_truetype to... no, it is the same
rasterizer; expect identical glyphs at the same size, and accept only what a side-by-side shows
to be 1.92's own hinting or packing change).

**Landed, with step 3's premise corrected.**

**The legacy atlas path does not exist in this tree.** `cimgui.h` is a *generated* header, and
`dear-imgui-sys 0.17.0` generated it with `IMGUI_DISABLE_OBSOLETE_FUNCTIONS` - which is why it
has no `ImFontAtlas_GetTexDataAsAlpha8`, no `Build`, no `SetTexID`. Worse, that define also
removes struct **fields** (`ImGuiIO::FontGlobalScale`, `ImDrawData::CmdListsCount`,
`ImFontConfig::PixelSnapV`), so it is not optional: the C++ has to be compiled with the defines
the header was generated with or the layouts Rust believes in disagree with the ones the library
was built with. So `IMGUI_DISABLE_OBSOLETE_FUNCTIONS` goes on here, not in Phase 3, and the
legacy path is gone with it. D3's byte-identity with fire's `simgui/cimgui.h` is confirmed (same
file, different line endings) and is what forces this.

The phase therefore carries what Phase 3 had assigned to it: the dynamic font model, and a host
that honours the 1.92 texture protocol. Both were going to happen; doing them here keeps the
property the phases exist for - the renderer is still wgpu, so every pixel of the capture diff
has one cause, which is the ImGui version.

- **`bite-imgui`** sets `ImGuiBackendFlags_RendererHasTextures` and asks for
  `ImTextureFormat_Alpha8`. `Context::texture_requests()` hands the host a create-or-replace or a
  destroy per texture, collected *inside* `Frame::render` before the draw commands are read -
  `ImDrawCmd_GetTexID` asserts that the identifier has been filled in, so the order is not a
  preference. Partial updates are reported as whole-texture uploads: ImGui keeps the full pixel
  buffer either way, and a sub-rectangle path in a renderer being deleted is not worth writing.
- **`font.rs`** registers six fonts (family x weight) instead of one per `Face`; `Face` and
  `FontId` are unchanged as the public API, `handles` just maps a face onto one of the six and
  `heights` onto the size to push. No glyph ranges, nothing rasterized at registration.
- **Sizing in logical space cost nothing.** The plan budgeted `RasterizerDensity` fiddling for
  this. It is not needed: with `RendererHasTextures` set, `imgui.cpp` drives the rasterizer
  density from `io.DisplayFramebufferScale` itself (`SetCurrentWindow`), which bite already sets
  to the display scale. Metrics stay logical, bitmaps follow the display, and `set_scale` is now
  one field assignment with no rebuild and no re-upload.
- **`app::texture_id` masks off the top bit**, which is now Dear ImGui's half of the identifier
  space (`bite_imgui::IMGUI_TEXTURE_ID_BIT`). The atlas and a thumbnail share one map in the
  renderer, and the two spaces are disjoint by construction rather than by the unlikelihood of a
  hash collision.
- **One real editor bug, found by a 1.92 assertion.** `checkbox_row` reserved its height but
  then moved the cursor two pixels past it, leaving the cursor outside the parent's content
  extent with no item to grow it. 1.92 reports that; it aborted four inspector scenes. Fixed by
  reserving the gap the row actually uses, which is layout-neutral.

**The capture diff: text only, and it is 1.92's.** All 50 scenes differ, 0.8-4.3% of pixels,
worst per-channel delta 238. Every differing pixel is a glyph: magnified 12x, the port dots, card
corners and every other piece of geometry are pixel-for-pixel identical, which is the evidence
that the renderer did not change. Magnified 4x, the showcase scene's type-scale block - every
stylesheet size, labelled - matches line for line in size, weight, position and advance width;
1.92 is a shade lighter. Two causes, both upstream's:

1. `ImFontConfig::OversampleH` defaulted to 3 in 1.90 and to auto (= 2 below 36 px) in 1.92.
2. 1.90 rasterized at a rounded size and corrected the *drawn* size back to exact with
   `ImFont::Scale`. 1.92 removed `ImFont::Scale` and rounds the drawn size unconditionally
   (`GetRoundedFontSize` is `IM_ROUND`, applied after every global factor), so a face now draws
   at a whole-pixel ascender-to-descender height - up to 0.48 px from where 1.90 put it.

Neither is worth fighting: 2 is not reachable through the API at all, and 3 -> 2 oversampling is
upstream's own judgement ("the difference between 2 and 3 is minimal") and saves atlas bytes the
memory target wants. `test_images/goldens/imgui192` is the new reference Phase 4 is checked
against.

### Phase 2 - The scaffolding, unwired

1. Vendor `sokol-rust` at b22a545 into `vendor/sokol-rust` (copy fire's directory; 3.9 MB) and add
   `exclude = ["vendor/sokol-rust"]` to the workspace for the lint reason fire's `Cargo.toml`
   documents. `sokol = { path = "../../vendor/sokol-rust" }` in bite-gui.
2. `windows = { version = "0.62", features = [Win32_Foundation, Win32_Graphics_Direct3D,
   Win32_Graphics_Direct3D11, Win32_Graphics_Dxgi, Win32_Graphics_Dxgi_Common] }` under
   `[target.'cfg(windows)'.dependencies]`.
3. `render/d3d11.rs`: fire's file. `Device::create` (hardware → WARP), `fill_environment`,
   `Swapchain::{new, size, resize, acquire, present}`, `SWAPCHAIN_FORMAT = Rgba8`. The
   `eprintln!` lines become `logging::warn`.
4. `bite-gui/simgui/`: fire's `simgui.c` and `sokol_imgui.h`; no `cimgui.h` copy - the include
   path points at `bite-imgui-sys/vendor/cimgui`, so there is one header. `build.rs` gets fire's
   `compile_simgui` with that include path and the vendored sokol's `src/sokol/c`. **The define
   list must match `bite-imgui-sys/build.rs` exactly** (`CIMGUI_DEFINE_ENUMS_AND_STRUCTS`,
   `CIMGUI_NO_EXPORT`, and `IMGUI_USE_WCHAR32` / `IMGUI_DISABLE_OBSOLETE_FUNCTIONS` if and only
   if the sys crate sets them): the two translation units share struct layouts. Put the list in
   one place and a comment in each build script pointing at the other, which is fire's posture.
5. `render/imgui.rs`: the `extern "C"` block from fire (`simgui_setup`, `simgui_render`,
   `simgui_imtextureid`, the `SimguiDesc` mirror), `simgui_setup_once` with
   `no_default_font: true`, `ini_filename: null`, `color_format: SWAPCHAIN_FORMAT`,
   `depth_format: None`, `sample_count: 1`, and the `RENDERER_HAS_TEXTURES |
   RENDERER_HAS_VTX_OFFSET` flags applied to bite's own context after setup.
6. `render/textures.rs`: `Textures { map: BTreeMap<u64, UiTexture> }` where the key is
   `app::texture_id(&key)` (the stable per-key id the editor already computes) and
   `UiTexture { image, view, id: u64 }` with `id = simgui_imtextureid(view)`. `upload(key,
   w, h, rgba) -> u64` returns the ImGui-side id; `free`, `free_where`, `contains` as today.
   The body of `upload` is fire's `upload_rgba` (`imgui.rs:640-665`).
7. `render/readback.rs`: 3d-review's `read_image_subresource`, reduced to one RGBA8 2D level.

*Done when:* `cargo build --release` succeeds with the new modules compiled and unused.

**Landed, and they are not unused: they are tested.** "Compiles" is a weak bar for glue to things
that only fail at runtime - a device that refuses, a `sg_environment` filled in wrongly, a
`simgui_desc_t` whose fields do not line up with the header's, a staging texture read at the wrong
pitch - and every one of those would otherwise first appear, tangled together, in a window that
draws nothing. So `crates/bite-gui/tests/render_stack.rs` walks the whole path once: device ->
`sg::setup` -> `simgui_setup` -> an offscreen pass cleared to a known colour with an ImGui
rectangle drawn over one quadrant -> `readback::rgba8`, checking the colours that come back. One
test, because `sg::setup` is process-wide. It needed `Frame::submit` from Phase 3, which is
additive - `Frame::render` still serves the wgpu path - so that came early.

It found two things the plan had wrong:

- **`simgui_shutdown` must never be called.** It ends by destroying the *current* ImGui context,
  which is bite's, and `bite_imgui::Context`'s own `Drop` then frees it again - a heap corruption
  inside `igDestroyContext`, several frames from anything that looks like the cause. Phase 3's
  "Exit: `simgui_shutdown()`, `sg::shutdown()`" is therefore just `sg::shutdown()`. There is no
  `shutdown` in `render/imgui.rs` at all, and a comment there says why; fire's teardown carries
  the same note, and fire never calls it either. What is given up is pipelines, shaders, a
  sampler, two buffers and ~7 MB of staging - all process-wide, all released by the process
  exiting, which is the only moment this would have been called.
- **sokol_imgui does not accept an Alpha8 atlas.** It hardcodes `SG_PIXELFORMAT_RGBA8` and
  asserts `tex->Format == ImTextureFormat_RGBA32`. So `TexDesiredFormat` is not a knob the host
  has, and `Fonts::prefer_coverage_texture` is gone: the atlas stays in 1.92's default RGBA32 on
  *both* renderers, so this cost is paid here rather than confounding Phase 3's capture diff.
  **It is 1 MB** (162.4 -> 163.4 MB working set), not the four-times-the-bytes the risk note
  feared, because the atlas is small to begin with. First-frame time does not move.

  The wgpu renderer draws the RGBA32 atlas through its colour path rather than its coverage path,
  which changes glyph edges slightly - 0.1-0.2% of pixels, worst delta 61, against the 0.8-4.3%
  of the ImGui upgrade itself. Magnified 20x on coloured text, where it would show worst, the two
  are equivalent and RGBA32 bleeds marginally *less* colour into the background. That is also
  simply how Dear ImGui renders through a standard `color * texel` backend, which sokol_imgui is.

`test_images/goldens/wgpu-final` is that capture - the last the wgpu renderer produces, and what
Phases 3 and 4 are checked against. `test_images/goldens/wgpu` remains the Phase 0 baseline.

### Phase 3 - The window on the new shell

`bite-imgui` first:

- `Frame::submit(self)`: marks the frame handed over and does nothing else. No `igRender`, no
  copy. `Frame::render() -> DrawData` stays for the wrapper's own tests (they assert on
  geometry) and is otherwise unused; the drop guard still closes an unsubmitted frame.
- `font.rs` goes dynamic: `Fonts::build` registers six fonts (family × weight) with
  `AddFontFromMemoryTTF(size_pixels = <any>, FontDataOwnedByAtlas = false)` and no glyph ranges
  (1.92 loads glyphs on demand). `FontId` becomes `(font index, logical size)`; `with_font`
  pushes `igPushFont(handle, size × em_to_pixel_height)`; `measure` passes the same size to
  `ImFont_CalcTextSizeA`. `texture()`, `clear_texture_data()` and `set_texture_id()` are
  deleted. `set_scale` becomes `style.FontScaleDpi = scale` and nothing else.
- `Context::new` no longer takes the atlas out of the context; the font-atlas claim is
  sokol_imgui's, made in `simgui_setup`.
- `IMGUI_DISABLE_OBSOLETE_FUNCTIONS` goes *on* in both build scripts now that nothing legacy is
  called; the compiler confirms it.

Then `platform.rs`:

- `Surface { window, swapchain: d3d11::Swapchain, textures: Textures }`. Delete
  `graphics_instance`, `wgpu::Surface`, `SurfaceConfiguration`, `WGPU_BACKEND`. Keep a
  `BITE_GPU=warp` override for the same reason (`Device::create` takes `force_warp: bool`).
- `run`: spawn the bring-up thread first thing (L1): `Device::create` → `sg::setup` with
  `environment.defaults = { color_format: SWAPCHAIN_FORMAT, depth_format: None,
  sample_count: 1 }` and `logger = slog_func` → `simgui_setup_once` → return `Device`. Hold
  the `JoinHandle` in `App`.
- `create`: join the handle after the window exists, `Swapchain::new(&device, &window, w, h)`,
  `Context::new(scale)` (which now applies the backend flags), `theme::apply_base_style()`.
  `upload_font_atlas` is deleted.
- `upload_pending`: `let id = textures.upload(app::texture_id(&key), w, h, &pixels)` and the
  returned `id` is what goes into `thumbnail.texture` / `PreviewImage.texture` - the only place
  the editor code changes. `editor.textures` keeps the key ids for freeing.
- `app::draw_frame` returns `()` and ends with `frame.submit()`.
- `Resized` → `swapchain.resize(w, h)`. `ScaleFactorChanged` → `context.set_scale(scale)`, no
  re-upload.
- `draw`: `let mut sc = sg::Swapchain::new(); sc.width/height = size; sc.sample_count = 1;
  sc.color_format = SWAPCHAIN_FORMAT;` `if !swapchain.acquire(&mut sc) { return }` (a zero-size
  or device-removed frame is skipped, as fire's is); `sg::begin_pass` with the
  `theme::GAP_COLOR` clear; `app::draw_frame(..)`; `simgui_render()` under `catch_unwind` so a
  UI panic cannot leave the pass open (fire's `imgui.rs:517-545`); `sg::end_pass();
  sg::commit(); window.pre_present_notify(); swapchain.present()`.
- Exit: `simgui_shutdown()`, `sg::shutdown()` after the loop, before the device drops.

*Done when:* the editor runs end to end - every panel, resize, minimise, DPI change,
fullscreen, thumbnails and previews arriving, text at every stylesheet size crisp - and the ttfp
harness reports the new numbers. Expect ~300 ms first frame before L3/L4 and ~60 MB working set.

**Landed, and both targets are already beaten: 145 ms and 57 MB.** The estimate of ~300 ms was
made against a 590 ms baseline that included its own measurement overhead; from the honest 424 ms
the win is the same size and lands lower.

Two corrections to the phase as written:

- **Acquire the render target *before* building the frame, not after.** The plan has the frame
  built, then `if !swapchain.acquire(..) { return }`. That crashes on the first restore from
  minimised: sokol_imgui is what *ends* an ImGui frame, so returning without rendering leaves the
  context open and the next `igNewFrame` asserts. The comment claiming the drop guard closes it
  is wrong too - `Frame::submit` marks the frame handed over, which is the whole point of it.
  Acquiring first means a skipped frame is simply never built.
- **No `simgui_shutdown` at exit**, per Phase 2. Just `sg::shutdown()`, with the device held in
  `State` so it outlives it.

`scripts/window-exercise.ps1` is the check for everything `--capture` structurally cannot reach:
it launches the editor and walks the real window through eight resizes, a minimise (a zero-size
client), a restore, a maximise and a `WM_CLOSE` from outside, then checks the exit code and that
nothing was logged above INFO. It is what found the crash above.

The measured breakdown says where the remaining time is, and it is no longer anything the editor
does:

```
   6.6 ms  main                        ─┐ all of this runs while the GPU comes up
  14.4 ms  Editor::new                  │
  45.3 ms  window created              ─┘
 136.5 ms  gpu device                   ← the critical path: D3D11 device creation, ~130 ms
 138.3 ms  gpu ready (sg + simgui)      ← sokol_gfx + sokol_imgui: 1.9 ms, against wgpu's 82 ms
 141.9 ms  gpu joined
 144.4 ms  swapchain                    ← 2.5 ms
 144.7 ms  imgui Context (fonts)        ← 0.26 ms; nothing is rasterized here
 151.9 ms  FIRST FRAME                  ← 7.2 ms, including the glyphs this frame is first to show
```

**This makes Phase 5 worth nothing measurable**, and that should be said plainly: the main thread
reaches "window created" at 45 ms and then waits 96 ms for the device. L3, L4 and L6 all shorten
work that is already entirely hidden behind that wait. They are worth doing for their own sake -
`Session::load` running twice is a real duplication - but not for time.

### Phase 4 - Offscreen capture

`smoke::capture`: after `stage`, bring the GPU up inline (no thread - the process does nothing
else), make a `render_target: true` `Rgba8` image at the physical size, a colour-attachment
`sg::View` on it, `sg::Pass { attachments: { colors[0]: view }, action: clear }`, run the frames
as today with `draw_frame` + `simgui_render` inside the pass for the last one, `end_pass`,
`commit`, `readback::rgba8(image, w, h)`, write the PNG, `simgui_shutdown`, `sg::shutdown`.
`capture_all` runs scenes in one process: keep one setup for the whole run and free per-scene
textures with `free_where`.

The 1.92 atlas is dynamic, so a scene's first frame uploads its glyphs; the six warm-up frames
already there cover it.

*Done when:* `--capture` output matches the Phase 1 output (same ImGui, different renderer).
Expect byte-identical: sokol_imgui's shader is the same multiply the owned one did. If alpha
blending rounds differently, accept ≤ 1 LSB per channel and say so here.

**Landed. Not byte-identical, but as close as makes no difference: every one of the 50 scenes
differs by at most 2 counts on one channel, across about 100 pixels in 1.6 million** (0.006%).
That is the rounding the plan allowed for, one count wider in two places.

One thing the plan's `capture_all` instruction would have got wrong: "keep one setup for the whole
run" is true of `sg::setup`, which is process-wide, but must **not** be extended to the ImGui
context. The first sokol capture run shared one context across all 25 scenes and five modal
dialogs came out 89% different - fully dimmed backdrops where the reference had none. The cause is
that `ImGuiContext::DimBgRatio` ramps a modal's dim in over ~10 frames and a capture runs 6, so
every scene *after* the first modal one inherited a ramp that was already at 1.0. A context per
scene - which is what the process did before the migration - restores it exactly. The graphics
stack is what has to be process-wide, not the context.

That is worth keeping in mind beyond the capture: a scene's dimmed backdrop is only partly drawn
at frame 6 in both the old renderer and the new one, so these images understate what a running
window shows. It is identical on both sides, which is what this phase is checking.

### Phase 5 - The rest of the launch work

In this order, measuring after each with the harness:

1. L3: `prune_cache` and the session log header to a thread; `Session::load` once.
2. L4: icon decoded in `build.rs`.
3. L6: parse a command-line `.bite` on a thread while the GPU comes up.

*Done when:* the *Results* table has a row per step and first frame is under the 300 ms target.

**L3 and L4 landed; L6 deliberately not done.** The target was already met by Phase 3, at 145 ms,
and the breakdown says why none of this can move it: the main thread reaches "window created" at
45 ms and then waits ~90 ms for the D3D11 device. Every item here shortens work that is already
entirely inside that wait. Measured after: **148 ms**, which is 145 ms plus noise.

So these were done for their own sake, and are worth it on those terms:

- **`Session::load` ran twice.** `Editor::new` read and parsed the session file, then
  `App::create` read and parsed it again for the window bounds and overwrote the first copy.
  `create` now reads `editor.session`.
- **The icon is decoded in `build.rs`** to raw RGBA in `OUT_DIR`, which `icon.rs` embeds and
  hands winit directly. The old decode sat on the serial path immediately before the window was
  created, and - worse - a re-exported or corrupt asset silently produced a window with the
  system default icon. Now it is a build failure. `png` stays a runtime dependency for
  `--capture`'s writer, and gains a build-dependency entry.
- **`prune_cache` is on its own thread.** It is a fraction of a millisecond on this machine's
  cache, so this buys nothing today; it is off the path because a cache large enough to matter is
  exactly the case where it would, and nothing waits on it either way.

**L6 was not done**, and should not be until there is a reason. Parsing a command-line `.bite` on
a thread is the most invasive of the three - it restructures how the initial workflow reaches
`App::create` - and unlike L3 and L4 it tidies nothing: `commands::open_path` already runs after
the first frame's state is built, so it is not on the first-frame path at all. It would be
speculative work against a number that cannot move.

**What would actually move it** is the ~90 ms of `D3D11CreateDevice`, which is the whole
remaining critical path and is the D3D11 runtime's, not the editor's. The plan's own isolated
benchmark measured 127 ms for a raw D3D11 device, so this is already at the floor for the API.

### Phase 6 - `bite-imgui` cleanup

With `Frame::render` unused by the app, decide whether the wrapper's tests want it or would
rather assert through `igGetDrawData` directly; either way delete `Vertex`, `Command`,
`DrawList`, `DrawData` from the public API if nothing outside the crate names them. Delete the
`Fonts` fields that only served the atlas (`handles`/`heights` stay; `scale` goes).

**Landed.** `Vertex`, `Command`, `DrawList`, `DrawData` and `Frame::render` are gone - nothing
outside the crate named them once `renderer.rs` did not exist. The wrapper's test asserts through
`ImDrawData::TotalVtxCount` instead of a copy it makes itself, and closes its frame by dropping
it, which is the path an unsubmitted frame takes in the editor.

`Fonts::scale` **stays**. The plan expected it to go with the atlas, but it does not serve the
atlas: `Context::set_scale` records it and the field is what `Fonts::scale()` answers, which is
the display scale the faces are being drawn at. Nothing else in the struct was atlas-only -
`handles` and `heights` are the face lookup and both are still load-bearing.

### Phase 7 - Remove wgpu

- Delete `renderer.rs`, `shader.wgsl`, `graphics_instance`, and `wgpu` and `pollster` from
  `Cargo.toml`.
- `smoke.rs` About scene: `("Dear ImGui", "1.90.9")` → `"1.92.9b"`, `("wgpu", "30.0")` →
  `("sokol_gfx", "<sokol_gfx.h version>")`.
- `THIRD_PARTY_LICENSES`: drop wgpu's tree, add sokol (zlib/libpng).
- `docs/native-editor-parity.md` / `rust-migration-progress.md`: one line each on the shell;
  `BITE-Rust-Migration-Plan.md`'s crate map loses `imgui-node-editor`.
- `cargo clippy --workspace` clean; the installer (`packaging/bite.iss`) needs no change - it
  ships the one exe, and the D3D11 runtime is part of Windows.

**Landed.** `renderer.rs`, `shader.wgsl` and `graphics_instance` are deleted, and `wgpu` and
`pollster` are out of `bite-gui`'s manifest - `cargo tree` finds no wgpu, naga, gpu-allocator or
pollster anywhere under it. The About dialog and the credits list name sokol_gfx; sokol_gfx is a
single-header library with no version of its own, so what identifies it is the pinned
`sokol-rust` revision, `b22a545`. `THIRD_PARTY_LICENSES` drops wgpu and pollster and gains sokol
(zlib/libpng, vendored). The installer needed no change, as expected.

The About and Credits scenes are the only two captures that move, because their text is what this
phase edits - both are checked by eye and read correctly. The other 46 stay within the 2 counts
Phase 4 established. Note that `smoke.rs` keeps its *own* fixed version list for the About scene,
separate from `commands::about_versions`, so that a capture does not depend on which ImageMagick
is installed; both have to be edited together.

### Phase 8 - macOS: done

Done on a Mac afterwards, as scoped. `render/metal.rs` is fire's, near-verbatim: a `CAMetalLayer`
on winit's `NSView`, `MTLCreateSystemDefaultDevice`, `nextDrawable` per frame. The seams the
earlier phases left were the right ones - `render/mod.rs` already gated the Windows files,
`compile_simgui` already switched `SOKOL_METAL` on `target_os`, and `SWAPCHAIN_FORMAT` was
indeed the one constant that had to be agreed. First frame from the packaged bundle is **163 ms**
at a 95 MB resident size, against the 300 ms target this migration set.

Four things differed from what this plan predicted, and they are worth recording:

- **`SWAPCHAIN_FORMAT` is `Bgra8` on macOS**, not `Rgba8`: a `CAMetalLayer` accepts a short list
  of formats and RGBA8 is not on it. That reaches further than the swapchain, because `smoke.rs`
  builds its offscreen capture target from the same constant - it has to, since sokol_imgui's
  pipeline is created once with it and a pass whose attachment disagrees fails validation. So
  `readback` swaps red and blue on the way out and the goldens stay one set of RGBA images for
  both platforms. `tests/render_stack.rs` is what holds this honest: its clear and rectangle
  colours have no two channels alike, so a swizzle missed or applied twice fails it.

- **The readback is a blit, not a map.** 3d-review's `getBytes` was not usable: sokol creates
  every colour-attachment image with `MTLResourceStorageModePrivate`, so the texture is not
  CPU-addressable at all. The Metal arm encodes a blit into a `StorageModeShared` buffer on
  sokol's own command queue and waits on it.

- **objc2 0.5 / 0.2, not the newest.** `rfd` and `arboard` pull objc2 0.6 and app-kit 0.3, but
  winit 0.30.13 pulls 0.5 with metal and quartz-core 0.2 - and `muda` is on the same family. So
  the older one costs nothing to depend on and let fire's files come across unedited; the newer
  one would have meant two families and a rewrite of every call.

- **`sg_swapchain` only needs the drawable.** `present` has no present call in it: `sg_end_pass`
  schedules `presentDrawable:` and `sg_commit` commits it, so the module only releases its own
  hold. Presenting again is a double present.

Beyond the renderer, macOS needed what no `cfg` had stood in for yet: a system menu bar whose
Quit routes through `Command::Exit` rather than AppKit's `terminate:` (`menubar.rs` - otherwise
Cmd+Q ends the process with the unsaved-document prompt unasked and the session unwritten), the
`application:openURLs:` hook that is the only way a double-clicked workflow reaches the app
(`openfiles.rs`), `../Resources` probes in `definitions_root` and `Magick::discover` for the
bundle layout, and real `timing.rs` arms (`proc_pidinfo`, `proc_pid_rusage`) in place of the NaN
this plan left there.

## Risks and things to check

- ~~**The ~22 ms steps.**~~ Settled in Phase 0: it was the pipe. The pre-window phases are
  0.6-5 ms apart on the file sink, `prune_cache` is 0.6 ms and `Editor::new` 5 ms, so **L3 is
  worth almost nothing** and should be done for tidiness rather than for time. What the
  breakdown does show is 35 ms between `Editor::new` and "window created" (L4 lives in there) and
  23 ms of font atlas (L7, free with D2).
- **The 1.90 → 1.92 API surface.** The wrapper touches more of ImGui than the list in Phase 1;
  the regenerated bindings and the compiler are the inventory, and Phase 1 exists so that
  inventory is worked through on a renderer that already works. Budget a day for it.
- ~~**Font sizing in logical space.**~~ Settled in Phase 1, and it costs nothing: with
  `RendererHasTextures` set, `imgui.cpp` sets the rasterizer density from
  `io.DisplayFramebufferScale` itself. Metrics are logical because the pushed size is logical;
  bitmaps follow the display. The mono-advance test passes and the scale-2 captures agree.
- **Atlas format and memory.** 1.92's default atlas is RGBA32 where 1.90's was Alpha8 - four
  times the bytes for the same coverage. `Fonts::prefer_coverage_texture` sets
  `TexDesiredFormat = Alpha8` in Phase 1 and the renderer's existing coverage path takes it
  unchanged; sokol_imgui accepts the same. Confirm the working-set target still holds after
  Phase 3.
- **sokol-rust API drift.** The vendored revision uses the 2025 *views* API (`sg::View` for
  textures and attachments, `Bindings::views`/`samplers`). Read `vendor/sokol-rust/src/gfx.rs`
  rather than upstream docs when a name does not match this plan.
- **`simgui_setup` and the current context.** It creates and destroys a context of its own, and
  every later `simgui_*` call works on whichever context is current (`igGetIO()`). bite has one
  context, made current for its lifetime, so this is simpler than fire's per-window suspension -
  but the backend flags must be set on *bite's* context, not assumed from setup.
- **`max_vertices`.** sokol_imgui sizes its vertex and index buffers once from `SimguiDesc`.
  The default (65536) is fine for the editor's chrome; a filmstrip of hundreds of thumbnails with
  rounded corners might not be - if a frame draws nothing past a point, this is why. Set to four
  times the default in Phase 2, which costs ~7 MB of staging and buys enough headroom not to have
  to diagnose it; revisit with a measurement of the busiest scene if that is ever not enough.
- **One sokol context per process.** `sg::setup` is global. The GUI and `--capture` never share
  a process, but any test that calls `capture` twice must not `setup` twice.
- **Nothing may touch ImGui between `simgui_setup` and `Context::new`.** `simgui_setup` creates a
  context of its own and leaves it current; `bite_imgui::discard_current_context` destroys it and
  leaves *none* current, so any ImGui call in that window reads through a null global. Nothing
  runs there - it is the last thing the bring-up thread does, and the context is made on the main
  thread after the join - but the two calls have to stay adjacent.
- ~~**Colour space.**~~ Settled in Phase 4: the captures agree to within 2 counts, so the UNORM
  swapchain and sokol_imgui's gamma choice line up as expected.
- **WARP.** Keep the fallback; the editor is used over RDP.
- **Device removed.** `acquire` returning `false` skips the frame and logs. A full device reset
  is out of scope, as it is in fire. Note that the skip has to happen *before* the frame is built,
  not after - see Phase 3.
- **Adapter choice.** `D3D11CreateDevice(None, HARDWARE, ..)` takes the default adapter; on a
  machine with a virtual display adapter first in the list that could be the wrong one. Fire has
  not hit it; if bite does, enumerate with `IDXGIFactory1::EnumAdapters1` and pick the one with
  the most dedicated memory.

## What this document got wrong

Kept because a plan's errors are the most useful part of it to the next one.

1. **"Use 1.92's legacy atlas path so the wgpu renderer keeps working."** The vendored `cimgui.h`
   is generated with `IMGUI_DISABLE_OBSOLETE_FUNCTIONS`, which removes struct *fields*, so the
   define is mandatory and the legacy path is not there to use. Phase 1 had to carry Phase 3's
   font work.
2. **"sokol_imgui accepts `ImTextureFormat_Alpha8` too."** It hardcodes `SG_PIXELFORMAT_RGBA8`
   and asserts. The atlas is RGBA32, which costs 1 MB rather than the feared 4x.
3. **"Exit: `simgui_shutdown()`, `sg::shutdown()`."** `simgui_shutdown` destroys the *current*
   ImGui context, which is bite's, and `Context::drop` then frees it again. It must never be
   called. fire never calls it either.
4. **"`if !swapchain.acquire(&mut sc) { return }`" after building the frame.** The acquire has to
   come first: `Frame::submit` hands the frame to sokol_imgui rather than closing it, so
   returning without rendering leaves the context open and the next `igNewFrame` asserts. This
   crashed on the first restore from minimised.
5. **"`capture_all` runs scenes in one process: keep one setup for the whole run."** True of
   `sg::setup`; false of the ImGui context. Sharing one let a modal's dim ramp carry between
   scenes and five captures came out 89% wrong.
6. **"L3 - file-system chores off the critical path", and the ~22 ms steps.** Both were artefacts
   of measuring through a redirected stderr pipe. `prune_cache` is 0.6 ms. The honest baseline
   was 424 ms, not 590.
7. **Phase 5 as a whole.** Written when the first frame was expected to land near 300 ms. At
   147 ms the main thread waits ~90 ms on `D3D11CreateDevice`, so nothing before the window is on
   the critical path and none of L3/L4/L6 can move the number. L6 was not done.
8. **"Delete the `Fonts` fields that only served the atlas … `scale` goes."** `scale` records the
   display scale, not anything the atlas owned. It stays.

None of these changed the destination. Every one of them was found by something that runs -
`tests/render_stack.rs`, `scripts/window-exercise.ps1`, `examples/capture_diff.rs`,
`scripts/ttfp.ps1` - rather than by reading, which is the argument for building those four first.
